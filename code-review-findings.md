# CoachOS V0.3 Code Review Findings

## Issues Found & Fix Plan

### 1. Version Mismatch (Low Priority)
- `server/index.ts` health endpoint reports `version: "0.2.1"` → should be `"0.3.0"`
- `package.json` name is `coach-os-v02` → should be `coach-os-v03`

### 2. Test Script Output Path Mismatch (Medium Priority)
- `tests/integration-test.sh` writes to `/home/ubuntu/coachOS/test-results.json`
- `tests/phase3-deep-test.sh` writes to `/home/ubuntu/coachOS/test-results-phase3.json`
- Both should write to the project directory

### 3. Session ID Mismatch in Recommendation Flow (Medium Priority)
- `recommendations.ts` evaluate endpoint: when session doesn't exist, creates a NEW session
  but then checks `getPendingRecommendation(sessionId)` with the ORIGINAL sessionId
  while the new session has a DIFFERENT id (generated by `generateId("sess")`)
- This means the pending-rec check uses the frontend sessionId, while the session store uses the generated id
- The `mainCoachSessionId` field stores the frontend sessionId, so the pending check works correctly
- However, the session used for evaluation is the newly created one with different id

### 4. Memory Leak Potential (Medium Priority)
- No session cleanup mechanism - sessions accumulate indefinitely
- No audit log size limit

### 5. Missing Error Handling in Frontend (Low Priority)
- `SpecialistChat.tsx` reads mainSessionId and recommendationId from query params but doesn't use them
- `HumanCoachPage.tsx` has no returnToMainAI call

### 6. Unused Import (Low Priority)
- `server/routes/coach-chat.ts` imports `addAuditLog` but never uses it

### 7. Concurrency Safety (Low Priority for MVP)
- In-memory store has no locking mechanism for concurrent access
